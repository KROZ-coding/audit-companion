- 审查日期：2026-10-17（本地时间，UTC+08:00）
- 对应版本：`a11b638`
- 审查范围：教师发题与题库导入、学生答题及批改结果恢复、启动入口与隧道相关配置。
- 本轮交付：问题报告、隔离验证结论及后续修复（见第六节）；修复过程未向正在使用的实例写入测试数据。

## 一、结论摘要

本轮确认 **5 项代码/交互问题，以及 1 项有明确触发前提的高风险启动配置问题**。其中，教师布置测验存在“返回失败但作业已经可见，重试后重复布置”的一致性缺陷；学生端存在切换试卷丢失答案、批改失败后恢复旧答案的问题。

**尚不能确认用户历史上通过网络隧道发布失败的唯一根因。** 当前证据不足以把历史故障直接归因于 Cloudflare、磁盘写入失败或模型超时。下面将隔离复现、源码确认和部署配置线索分别说明。

这里的“教师发题”需要区分：已复现的一致性问题位于 **组卷并发给学生的 `/api/quiz/assign`**，不能直接等同于题库中单题的“发布”操作，也不能代替对用户当时失败请求的取证。

优先级含义：P1 为应在真实教学继续扩大使用前优先处理的问题；P2 为应纳入近期修复的问题。

| 编号 | 优先级 | 问题 | 证据类型 |
| --- | --- | --- | --- |
| 1 | P1 | 布置测验保存失败后仍可见，重试产生重复作业 | 隔离接口故障注入复现 |
| 2 | P1 | 切换试卷可能丢失新输入，慢加载时可能清空已有文本草稿 | 实际前端函数＋模拟 API 隔离时序复现 |
| 3 | P1 | 批改失败后新草稿保存成功，恢复时却显示旧提交 | 隔离接口完整请求链复现 |

| 6 | P2 | 课程权限撤销后，旧导入预览仍可确认写入 | 隔离接口权限变更复现 |

## 二、详细问题

### 1. 布置测验保存失败后仍对学生可见，重试产生重复作业

**影响**：教师收到发布失败提示，但学生已经能看到作业。教师按常见操作重试后，会产生重复作业；失败请求留下的状态还可能被之后的成功保存一并持久化。

**触发前提**：启用了持久化，并且布置测验后的保存阶段失败。本轮通过注入保存失败验证控制流，没有在线上制造磁盘错误。

**代码位置**：
- [server/app/routers/quiz.py:180–213](../server/app/routers/quiz.py#L180-L213)：生成新的作业 ID，将作业和学生测验写入内存。
- [server/app/main.py:114–121](../server/app/main.py#L114-L121)：接口处理后保存；失败返回 `503 persistence_failed`，但没有撤销前面的业务变更。

**隔离复现**：使用临时数据目录启用持久化，仅让第一次布置测验的保存结果返回失败。

1. 教师提交布置请求，响应为 `503 persistence_failed`。
2. 学生查询作业，已经能看到 **1 份**。
3. 教师用相同内容重试，响应为 `200`。
4. 学生查询作业，变为 **2 份**。
5. 重新加载持久化数据，两份作业均存在。

**原因**：业务修改与可靠提交不是同一个原子操作；失败后内存状态仍可见。布置接口也没有请求幂等保护，每次请求都会创建新的作业。

**建议**：
- 将作业、学生测验及相关索引作为一个原子提交；失败不留下可见的半成功状态，避免用整库回滚误伤并发请求。
- 增加可持久化的请求幂等键，使同一次布置在超时、断线或保存异常后的重试返回同一个作业结果。
- 前端提供核实布置结果的入口。禁用重复点击只能辅助，不能解决“请求已执行但响应未收到”的情况。

**验收重点**：保存失败时不可出现部分发布；同一幂等请求重试只产生一份作业；提交成功但响应丢失后重试仍不重复；重新加载后的状态一致。

### 2. 切换试卷会丢失尚未自动保存的答案，慢加载时可能覆盖已有草稿

**影响**：学生快速切换测验时，刚输入的答案可能没有保存；网络较慢时，还可能把原试卷已有的文本草稿覆盖为空。

**代码位置**：
- [智能学伴演示页.html:2029–2038](../智能学伴演示页.html#L2029-L2038)：打开另一份试卷或开始随机测验时，先清空原答题区域。
- [智能学伴演示页.html:2082–2098](../智能学伴演示页.html#L2082-L2098)：延迟保存依赖执行时的全局当前试卷和页面输入，而非安排保存时的试卷与答案快照。

**隔离复现**：从实际 HTML 提取相关函数，用 Node VM、最小 DOM、可控定时器及模拟 API 执行；模拟草稿接口对齐未知题号检查、非 `ongoing` 拒绝、未变内容不更新时间和整份替换规则。这不是完整浏览器 GUI 或真实后端联调实测。

1. 试卷 A 的文本答案已保存为 `A-old`；`t=0` 改为 `A-new`，`t=500ms` 打开 B，原自动保存定时器在 `t=2000ms` 执行。
2. B 快速加载（100ms 返回）时，定时器向 `/api/quiz/B/draft` 保存的是 B 自己的答案 `B-old`；返回 A，仍为 `A-old`。本轮没有复现把 `A-new` 串写到 B。
3. B 慢速加载（3000ms 返回）时，定时器执行时当前对象仍指向 A，但原输入框已经移除，向 `/api/quiz/A/draft` 提交空文本并覆盖 A 的草稿。此分支分别覆盖简答、填空和案例文本题。
4. 已发出的 A 保存请求在切换到 B 后返回，会更新当前 B 的保存提示，界面未校验响应所属试卷。

后端草稿接口的整份替换规则见 [server/app/routers/quiz.py:352–378](../server/app/routers/quiz.py#L352-L378)；文本输入仅安排延迟保存、未同步更新答案对象的前端逻辑见 [智能学伴演示页.html:2000–2012](../智能学伴演示页.html#L2000-L2012)。

**原因**：待执行的保存任务没有绑定原试卷 ID 和答案快照；切换也没有先完成原试卷保存或妥善取消该任务。

**建议**：按试卷维护草稿状态；保存任务携带固定的试卷 ID、答案快照及版本。切换前先采集并保存原答案，不能在清空 DOM 后重新读取。处理旧请求晚返回时，不应更新新试卷的保存提示或覆盖更新后的状态。

**验收重点**：覆盖快速切换、慢加载、请求乱序、保存失败后继续编辑；A/B 的答案不能串写，新的文本不能被空值或旧请求覆盖。

### 3. 批改失败后新草稿保存成功，恢复作答时仍显示旧提交

**影响**：学生收到批改失败后继续修改，草稿保存接口返回成功；重新进入测验却看到旧答案，容易误认为修改已经丢失，并可能基于旧答案再次提交。

**代码位置**：
- [server/app/routers/quiz.py:419–423](../server/app/routers/quiz.py#L419-L423)：批改失败后恢复为 `ongoing`，但保留原 `submitted_answers`。
- [server/app/routers/quiz.py:338–347](../server/app/routers/quiz.py#L338-L347)：恢复时优先返回旧提交，同时过滤与其重叠的草稿。
- [智能学伴演示页.html:2003–2004](../智能学伴演示页.html#L2003-L2004)：前端合并答案时也让旧提交覆盖草稿。

**隔离复现**：使用 FastAPI TestClient 完整执行以下请求链。

1. 提交“答案 1”。
2. 注入批改异常，提交接口返回 `503`，测验恢复可作答状态。
3. 学生修改为“答案 2”，草稿保存返回 `200`。
4. 重新请求测验，得到 `status=ongoing`、`saved_answers` 中的“答案 1”，以及 `draft_answers={}`。

**结论边界**：已确认的是新草稿在恢复响应和界面中被旧提交遮蔽；不能将该现象直接表述为新草稿已经从底层存储删除。

**建议**：明确区分“本次批改尝试的提交快照”和“当前可编辑草稿”。批改失败回到可编辑状态后，后续新草稿应按版本或编辑时间恢复；旧提交可保留为历史，但不能继续无条件覆盖当前答案。前后端必须采用一致的优先规则。

**验收重点**：批改失败后修改并保存，刷新、重新登录或重新打开测验均恢复最新答案；重新提交使用最新答案，失败尝试的历史仍可追溯。

### 4. 普通 BAT 新建服务默认未启用持久化

**影响**：如果直接用普通 BAT 新建服务，且没有外部环境覆盖，业务状态只保留在当前进程中；重启后可能表现为学生、题目或作业不见了。不同启动方式还可能读取不同数据位置，造成“本地与公网不是同一份数据”的感受。

**明确前提**：本结论针对脚本实际新建进程的路径，不等于已经确认正在运行的实例关闭了持久化。BAT 会跳过已健康的服务；已有进程也可能继承不同环境变量。

**证据**：
- [启动服务.bat:34](../启动服务.bat#L34) 直接启动 Uvicorn，没有设置 `PERSISTENCE_ENABLED`。
- 当前 `server/.env` 未设置 `PERSISTENCE_ENABLED` 或 `DATA_DIR`。
- [server/app/config.py:138–139](../server/app/config.py#L138-L139) 的默认值分别为 `./data` 和 `false`。
- [server/app/store.py:152–160](../server/app/store.py#L152-L160) 使用 `store.sqlite3`，且只有启用持久化才加载数据。
- [start_audit_companion.ps1:25–27](../start_audit_companion.ps1#L25-L27) 则明确设置 `PERSISTENCE_ENABLED=true`。

**建议**：统一正式教学入口，显式声明持久化和数据目录，并在启动状态中显示生效值、实例标识及数据库位置。对于已有内存数据的实例，先评估导出或迁移方式，不能只切换配置并立即重启。

**验收重点**：在隔离环境分别通过正式支持的入口启动、写入测试数据并重启，验证数据仍存在；切换部署方式时应有明确的数据迁移与备份说明。

### 5. 正式测验缺少完整结果回看入口，刷新或重新加载后无法从界面重新打开

**影响**：正式测验提交后当场可以看到逐题结果，但已完成作业列表只有状态，没有查看按钮；结果区域在页面刷新或测验页面重新加载后清空。教师后续复核的完整结果也缺少从该列表重新进入的路径。

**代码位置**：
- [智能学伴演示页.html:1992–1997](../智能学伴演示页.html#L1992-L1997)：非 `ongoing` 作业渲染为状态标签，没有查看入口。
- [智能学伴演示页.html:2044–2046](../智能学伴演示页.html#L2044-L2046)：重新加载测验页会清空结果区域。
- [智能学伴演示页.html:2117–2130](../智能学伴演示页.html#L2117-L2130)：正式测验完整结果的查询与展示挂在当前提交调用中，渲染依赖本次提交的局部 `answers`。
- [server/app/routers/grading.py:14–26](../server/app/routers/grading.py#L14-L26)：后端已有按 `session_id` 查询批改结果的 `/api/grading/{session_id}/status`，并检查本人或课程权限；问题不是缺少 `grading_id`。
- [server/app/routers/helpers.py:39–50](../server/app/routers/helpers.py#L39-L50)：学生批改结果响应不包含 `submitted_answers` 作答快照，不能直接替代当前提交调用中的答案对象。

**验证方式及边界**：隔离执行实际前端函数，确认模拟提交后能显示结果、执行 `renderQuiz()` 后结果区域为空，且非 `ongoing` 作业没有查看按钮；未完成此场景的 GUI 实测。源码确认单纯切换导航页不重载正式测验、不主动清空其结果，因此不能写成“一离开页面结果就消失”。学情页已有成绩摘要和有限错题回顾，但没有整卷结果查看操作，见 [智能学伴演示页.html:2734–2740](../智能学伴演示页.html#L2734-L2740)。问题是正式测验完整结果的回看链路缺失，不是结果未存储或完全没有历史。

**已有功能不在此问题范围**：AI 练习已有“练习历史”及“查看”入口，见 [智能学伴演示页.html:2154–2164](../智能学伴演示页.html#L2154-L2164)，已批改结果恢复见 [:2194–2197](../智能学伴演示页.html#L2194-L2197)、[:2229–2233](../智能学伴演示页.html#L2229-L2233)；历史与详情接口见 [server/app/routers/practice.py:277–299](../server/app/routers/practice.py#L277-L299)。正式测验中的“继续上次练习”列表只列 `ongoing`，不能据此推出整个应用没有练习历史。

**建议**：为正式测验中已提交、待复核和已完成状态提供适合其状态的查看入口，接通已有的按 `session_id` 查询结果接口；在学生可见响应中补充该次提交的作答快照，使结果展示不再依赖当前页面的局部答案对象。继续遵守学生可见范围和教师复核规则，不重复建设 AI 练习已有的历史入口。

**验收重点**：刷新、重新登录后仍能打开自己的正式测验完整结果；教师复核后的更新可再次查看；不能看到他人的结果。

### 6. 课程权限撤销后，旧导入预览仍可确认写入

**影响**：教师在仍有权限时创建导入预览，课程转交其他教师后，原教师仍能确认该预览，向已无权管理的课程新增题目。

**代码位置**：
- [server/app/routers/bank.py:363–365](../server/app/routers/bank.py#L363-L365)：预览时检查目标课程权限。
- [server/app/routers/bank.py:400–426](../server/app/routers/bank.py#L400-L426)：确认时检查预览归属，但未重新验证目标课程的当前权限。

**隔离复现**：
1. 原教师为自己负责的课程创建有效导入预览。
2. 管理员将课程转交另一位教师。
3. 原教师读取课程题库返回 `403`。
4. 原教师确认旧预览仍返回 `201`，课程中新增草稿题。

**结论边界**：这是撤权后的越权写入，不是绕过审核直接发布题目。

**建议**：确认写入前统一检查所有目标课程是否存在、当前用户是否仍有授课权限；检查与写入保持一致，任何一行失败都不能部分导入。

**验收重点**：课程转交、删除或权限变化后旧预览不能越权确认；多课程导入不能只写入其中一部分。

## 三、网络隧道与部署差异：已知事实和未确认项

### 3.1 启动入口并不等价

以下是配置事实，不是当前运行状态的实测清单。

| 启动方式 | 默认宿主端口 | 持久化配置 | 默认数据位置 |
| --- | --- | --- | --- |
| 普通 BAT | 8000 | 未显式启用；无覆盖时为 false | 启用后通常为 `server/data` |
| PowerShell | 8000；占用时改为 8001 | 显式 true | 无目录覆盖时为 `server/data` |
| Quick Docker | 8000，可用 `QUICK_PORT` 修改 | 显式 true | 独立命名卷 `quick-data`，容器内 `/data` |
| Sim Docker | 18000，可用 `SIM_PORT` 修改 | 显式 true | 宿主 `server/sim-data`，容器内 `/data` |

依据：[start_audit_companion.ps1:20–27](../start_audit_companion.ps1#L20-L27)、[server/docker-compose.quick.yml:22–44](../server/docker-compose.quick.yml#L22-L44)、[server/docker-compose.sim.yml:31–45](../server/docker-compose.sim.yml#L31-L45)。

- 原生数据、Quick 命名卷与 Sim 目录不是同一份数据；切换入口不等于完成迁移。
- 隧道相关配置注释指向宿主 `localhost:8000`。本地应用回退到 8001，或修改 Quick 的宿主端口，不代表公网隧道会同步改向；当前隧道的实际目标仍需以生效配置为准。
- Quick 和 Sim 的健康检查只请求 `/health`，不能证明公网链路或真实模型调用成功。
- Sim 基础配置不能直接当作假模型环境；只有 `docker-compose.sim.fake.yml` 覆盖配置明确跳过 `.env` 并指向内置假模型。

### 3.2 模型等待预算与代理读取超时存在潜在不匹配

- 当前 `server/.env:6`、`:9` 分别配置单次模型超时 **180 秒**、总预算 **420 秒**。不是代码默认的 30/360 秒。
- 环境加载不会覆盖已有进程环境变量，因此上述文件值不等于已实测的运行中实例值。
- [server/app/config.py:170–173](../server/app/config.py#L170-L173) 的默认值包括最多 3 次尝试、并发 32、队列 60、排队超时 240 秒；这些默认值也可能被运行环境覆盖，不能简单相加当作所有请求的实际耗时。
- [server/nginx.conf.example:43](../server/nginx.conf.example#L43)、[:53](../server/nginx.conf.example#L53)、[:63](../server/nginx.conf.example#L63) 的 `proxy_read_timeout` 为 120 秒。它是上游读取空闲时限，不是请求总时长；只有该示例实际生效且上游连续无数据超过时限时，才能据此解释代理先断开。
- 已审查的 `/api/quiz/assign` 业务路径本身不执行模型出题，不能仅凭模型超时配置解释这一路径的发布失败。

**判定**：以上是慢模型请求在代理链路下的排查线索，不是已确认的线上超时复现。不能用单纯调大超时替代持久化一致性、幂等与学生草稿问题的修复。

### 3.3 本轮没有完成的线上归因

### 6.1 补充修复：首轮修复漏掉的同类路径（2026-10-17 二次复核）

首轮修复只覆盖了“布置测验”，但题库本身的“送审/审核发布/下架/新建/删除”仍是旧写法。实测确认了与用户症状直接对应的缺陷：

- 审核发布时若落盘失败，接口返回 `503`，但内存里的题目状态已经变成 `published`；
- 下一次任意成功保存会把这个“失败”的发布写进磁盘，等于发布在用户不知情时成功；
- 教师按提示重试时，题目已不在 `reviewing`，于是得到 `409 invalid_transition`——正是“发布不了题目”的体验。

补充修复内容：

| 项目 | 修复 |
| --- | --- |
| 题库写操作 | 新建、送审、审核、下架、删除统一改为“改内存 + 立即落盘”，失败时回滚字段、撤销本次审计并返回 `503`（`server/app/routers/bank.py`）。 |
| 提交批改结果 | 批改完成后显式落盘；失败时移除结果、把提交内容转为草稿并回到 `ongoing`，学生可重新提交（`server/app/routers/quiz.py`）。 |
| 关闭/刷新页面 | `pagehide` 时用 `sendBeacon` 补发待保存草稿，覆盖“输入后立刻关页面”的丢失路径（`智能学伴演示页.html`）。 |
| 幂等键 | 幂等键同时绑定请求内容；同一键换题目/学生/截止时间会返回 `409 idempotency_key_reused`，不再错误复用旧作业（`server/app/routers/quiz.py`）。 |
| 结果入口 | “查看结果”只在作业确实有 `result_id` 时出现，避免点击后 404（`智能学伴演示页.html`）。 |
