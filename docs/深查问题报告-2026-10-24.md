## 二、P0-1：隧道下"发布不了题目"的最吻合根因

**机制**：`same_origin_writes` 中间件（main.py:124-150）对写请求校验 `Origin` 与 `Host` 头一致性，不一致时回退到 `cors_origins` 白名单。当前部署实际运行在 development 模式（.env 未定义 APP_ENV，且按 main.py 的 production 前置检查，现有配置+演示账号密码也无法以 production 启动），`cors_origins` 默认仅 `http://localhost:5173` 与 `"null"`，**不含公网域名**。

**触发条件**：任何一层把 Host 改写为 `localhost:8000`（cloudflared 的 httpHostHeader 覆盖、误加的反代、某些 ingress 配置），或浏览器以与隧道域名不同的 origin 发起写请求。

**隔离复现**（临时目录 TestClient，Origin=`https://audit-companion.xyz`）：

| 场景 | Host 头 | 结果 |
| --- | --- | --- |
| cloudflared 默认保留公网 Host | `audit-companion.xyz` | 200 放行 |
| Host 被改写 | `localhost:8000` | **403** `cross_site_request`（登录接口） |
| 同条件下的布置接口（未登录） | `localhost:8000` | **403**——同源中间件先于鉴权拦截，即"发布不了"的直接形态 |
| 读接口 /health | `localhost:8000` | 200 不受影响 |
| 不发 Origin 的客户端 | `localhost:8000` | 200 放行（误拒只发生在 Origin/Host 失配） |

**影响**：一旦发生即全站写操作瘫痪（学生交卷、教师布置、登录全部 403），且 403 响应不含任何诊断信息，运维无法从响应判断是"同源校验拒绝"还是权限问题。这解释了"时好时坏"的形态：Host 保留时一切正常，任何配置漂移立即全站故障。

**结论边界**：本轮为隔离复现，未在实际隧道链路上抓到改写证据；但该路径是当前代码中唯一能把"所有写请求"确定性拒绝、且与隧道拓扑直接相关的机制。

**建议**：① `cors_origins` 支持环境变量注入公网域名（部署手册同步）；② 同源中间件拒绝时输出含 origin/host 实际值的日志并给可辨识的响应码细节；③ 启动时自检"公网域名是否在白名单"并打印告警。三项均为低风险小改。

## 三、P1-1~P1-4：剩余写接口的落盘失败行为（故障注入复现）

注入方式：包装 `store.save_if_dirty_async` 首次返回 False（同步端点的落盘全靠 persist_state 中间件这一次调用；失败后中间件把端点的 2xx 替换为 503，内存变更已发生）。每个场景独立临时实例。

| 接口 | 503 后实际状态 | 重试结果 | 用户视角 |
| --- | --- | --- | --- |
| 改密码 | 新 hash 已生效、全部旧会话已删 | 旧密码 401 / 新密码 200 | "改密失败"却再也登不上旧密码；除非自己试新密码，否则以为账号坏了 |
| 学生注册 | 待审用户已在内存、在教师审批列表可见 | 409 `registration_conflict` | "注册失败"，无法重新提交；需教师告知"其实收到了" |
| 入学审批 | 学生已激活（实测可登录） | 404 `registration_not_found` | 教师以为没批成，重试报"不存在"；学生却已经进来了 |
| 加课 / 退课 | 名单已变更 | 409 `already_enrolled` / 404 | 同上，动作生效但界面报失败 |
| AI 练习提交 | 已判分入内存（GET 可见成绩） | 409 `practice_already_submitted` | 与修复前的测验提交同型；结果可见，严重度中等 |
| AI 答疑提问 | 回答已生成入历史、用量已计次 | 可重试 | 重试=重复计费+历史重复入库（真实模型时烧两次额度） |
| 删文档 | **文件已物理删除**，磁盘记录仍在 | 404 | 重启后记录复活指向缺失文件；文件内容不可恢复 |
| 删用户 | 内存已删，磁盘未删 | 404 | 见下方两种结局 |

**重要补充（本轮新确认的自愈行为）**：503 后内存变更虽未落盘，但脏计数保留，**下一个任意成功写请求会把积压变更一并补落盘**（实测：删用户 503 后，紧随的重试请求虽返回 404，其中间件保存把删除持久化了）。因此真实丢失窗口是"503 后、下一个成功写请求前进程崩溃"；而文件 unlink 不参与该机制——文件删了就是删了，这是删文档/删用户场景比其他 B1 更重的原因。

**建议**：把这批接口按 bank.py `_commit_or_rollback` 模式统一改造（改密码、注册、审批、加退课、练习提交、chat ask、admin 用户/课程增删）；文件删除改为"先落盘成功、再删文件"（失败时文件保留，记录已删，孤儿文件可用启动清扫回收——顺带解决现存孤儿 .tmp/.xlsx 无清扫问题）。

## 四、P1-5：会话过期与前端 401

代码确认：会话固定 7 天 TTL（config.py:141），`get_session` 只查不续期（store.py:745-751）；同一账号多处登录共存，仅改密码时清除。

前端取证（提取实际页面函数，Node VM 模拟 401 响应）：

- 提交测验遇到 401：成绩区显示 `ERROR:请先登录`，页面不跳转登录、无弹窗引导，提交按钮恢复可点，学生留在过期页继续操作。
- 草稿自动保存遇到 401：提示为通用"自动保存失败，将继续重试"，与网络故障不可区分；重试计时器持续对已失效会话发请求（实测连发 2 次以上）。
- `apiRequest` 对 401 无任何专门分支（html:1796-1814），与其他错误同一 catch 处理。

**建议**：`apiRequest` 捕获 401 时统一处理——保留当前页面内容与草稿快照、给出"登录已过期"的显式引导（跳登录并在登录成功后回到原视图）；草稿保存区分 401（停止重试）与其他错误（继续重试）。后端可选：会话滑动续期（每次请求刷新 TTL）或到期前预警。

## 五、P2：学期规模与运维面

**P2-1 写请求延迟（隔离实测）**：合成学期数据（50 生 × 1500 已交卷会话 × 10 题 + 1 万条聊天 + 5 千审计，全量 JSON 16MB）后，同一次草稿保存从空库 9ms 升至 **437ms**（含中间件等待全量落盘）；落盘经单 worker 线程串行，交卷高峰 N 个并发写按 N×~440ms 排队；excel 快照路径在 store.lock 内 deepcopy 全量相关状态实测 **203ms**，期间所有请求阻塞。数据继续增长则线性恶化。

**P2-2 无界集合（代码确认）**：已交卷会话（内嵌整份题目 dict）、results、AI 练习会话（仅显式登出清理，cookie 自然过期则永不清）、点名记录均无自动归档；仅 admin 手动 `cleanup_history`。chat 历史（200 条/人）、审计（5000 条）、excel 快照（20 份/人）、登录会话有过界。

**P2-3 注册限流连坐（配置+代码确认）**：注册限流键为 `client.host`（auth.py:88-95 → store.py:861-875），限额 100 次/小时（config.py:144-148）；应用不读 X-Forwarded-For、uvicorn 未开 proxy-headers，经隧道所有用户共用同一来源地址——集中注册超 100 人即整班 429。登录锁定仅按用户名，无连坐（已确认安全）。

**P2-4 运维静默风险（代码确认）**：`save()` 静默吞掉 OSError（store.py:414-417），全应用无服务端日志，磁盘故障期间只能靠学生报障发现；恢复后自动愈合。多进程部署无任何防呆检测（四个启动入口均单进程，但 `--workers 2` 不会被拦截，后果是内存双份+单行 BLOB 互踩）。

**建议**（按性价比排序）：save 失败打 ERROR 日志并暴露到 /health；写请求的落盘改为只在关键路径同步等待、其余接受延迟落盘（或快照分表）；启动时对显然是开发用的配置（development 模式+公网域名访问）打印告警；注册限流改"用户名+IP 双键"或经隧道场景放宽；学期末手动归档前先提供一键导出备份。
